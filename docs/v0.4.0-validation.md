# v0.4.0 validation and tuning results

Date: 2026-09-08. Target: clean 1080p30 camera motion with exact video/mask pairing.
Hardware: Intel Core Ultra 7 265K, NVIDIA RTX 5070 Ti (16 GiB), driver 595.84;
native OBS/libobs 32.2.0, NVIDIA OpenGL, ONNX Runtime 1.29.0, CUDA backend.

## What changed

- Opt-in quality button applies the 1080p30 RVM configuration while preserving model,
  device, CPU threads, and preview. Existing defaults and saved filter settings stay intact.
- Five-second diagnostics distinguish completions, distinct presented capture pairs,
  repeat presentations, pending replacements, processing, queue wait, and displayed age.
- Optional RVM foreground RGB travels with the same alpha, capture identity, and generation.
  Invalid precision, dimensions, or non-finite colors fail visibly. The option defaults off.
- Official ResNet50 FP32/FP16 download pins and opt-in packaging extend the existing RVM path.
- Matched rendering explicitly uses premultiplied blending. A half-transparent fixture
  exposed a second alpha multiplication inherited from the surrounding render state:
  green RGBA (0,128,0,128) was previously rendered as (0,64,0,128). The corrected path
  preserves (0,128,0,128); source-RGB mode preserves (128,40,0,128).
- PNG sequence replay performs decoding on a worker with a three-image cache. The offline
  sequence tool exports alpha, transparent cutouts, three-background comparisons, and timings.

## Model processing comparison

Each run used the same already-composited 1920×1080 frame on CUDA, 100 repeated iterations,
with the first 10 excluded. Automatic RVM downsampling was used. Values include tensor
preparation, inference/transfers, alpha conversion, and optional foreground conversion.
They exclude OBS capture/rendering and are **not matte-quality or live-FPS evidence**.

| Model | Input limit | Foreground RGB | Mean processing | p95 processing |
| --- | ---: | --- | ---: | ---: |
| MobileNetV3 FP32 | 1280 | Off | 6.87 ms | 7.54 ms |
| MobileNetV3 FP32 | 1920 | Off | 13.03 ms | 13.61 ms |
| MobileNetV3 FP16 | 1920 | Off | 17.49 ms | 18.03 ms |
| ResNet50 FP32 | 1920 | Off | 14.88 ms | 15.50 ms |
| ResNet50 FP16 | 1920 | Off | 16.82 ms | 17.49 ms |
| MobileNetV3 FP32 | 1920 | On | 25.85 ms | 26.49 ms |

Source: `artifacts/v040/model-timings.json`; it records each model checksum.
FP16 is not the faster pipeline on this build. Foreground RGB roughly doubles the tested
MobileNetV3 FP32 processing cost. Neither ResNet50 nor foreground RGB becomes the default
based on these timing measurements alone.

## Ten-minute replay with encoding load

### Final build: acceptance passed

The reproducible script ran the corrected module for **600 seconds**, with a 30 FPS
sequence source, 60 FPS/1080p OBS output, MobileNetV3 FP32 at a 1920 input limit, automatic
downsampling, matching/readback on, and foreground colors off. A separate paced NVENC
H.264 encoder ran throughout and emitted no warnings. All 591 sampled windows after
the first ten seconds passed the numeric acceptance gate.

| Measurement | Result |
| --- | --- |
| Completed masks | 30.0/s, in every steady-state five-second window |
| Distinct presented plugin capture pairs | 29.8–30.2/s across windows; 30.0/s average |
| Rendered matched output | 60.0 frames/s; 36,000 matched presentations |
| Displayed mask age | 37.80 ms whole-run mean; rolling p95 35.35–50.18 ms |
| Processing p95 | 13.52–18.82 ms across windows |
| Queue-wait p95 | At most 0.20 ms; zero replaced waiting frames |
| Readback | 1.35 ms mean; 2.31 ms maximum |
| Retained video textures | 3; zero cache misses |
| Sequence delivery | Zero decoder underruns or errors |
| RSS after warmup | 1,279,500–1,279,784 KiB; plateau, less than 0.3 MiB spread |

Sources: [summary](../artifacts/v040/final-soak/summary.json),
[one-second samples](../artifacts/v040/final-soak/result.png.timings.csv),
[input/model metadata and hashes](../artifacts/v040/final-soak/metadata.json), and
`artifacts/v040/final-soak/obs.log`. The complete libobs process (including setup and
teardown) reported 21 skipped output frames out of 36,134 (0.1%). The measured interval
still produced the 36,000 matched presentations reported above.

This is **isolated replay of the supplied finished composite**, with a separate encoding
load. It excludes camera buffering, the user's complete scene, microphone timing, and
screen latency. It demonstrates bounded processing behavior, not natural-motion matte
accuracy or complete live-scene acceptance. Each p95 is from a rolling five-second window.

### Earlier run, retained for comparison

The initial 600-second run replayed the supplied composite at 30 FPS with 1920×1080
RVM MobileNetV3 FP32 input, matching and immediate readback, 60 FPS/1080p OBS output, and
a separate paced NVENC H.264 encoding process. The display used NVIDIA OpenGL, not llvmpipe.
This test left the user's scene collection and camera controls unchanged.

- Whole-run completed rate: **30.0 masks/s**; output: **60.0 frames/s**.
- Mean displayed mask age: **39.22 ms**.
- After ten seconds, five-second completion rates were **29.8–30.2 masks/s** and
  five-second displayed-age p95 was **35.32–50.17 ms**.
- Three retained video textures; zero cache misses; zero replay decoder underruns.
- RSS after warmup: **1,279,392–1,279,972 KiB**, a plateau with less than 0.6 MiB spread.
- Mean readback: **1.31 ms**; maximum **5.28 ms**. No growing inference queue.
- The numeric 29 masks/s and p95 <75 ms acceptance gate passed throughout measured windows.

Sources: `artifacts/v040/soak-10min.log` and `soak-10min.png.timings.csv`.
The initial external encoding load stayed alive but logged DTS warnings while looping
the short MKV. The reusable benchmark script regenerates constant-rate timestamps to
avoid that boundary issue. These warnings were from the load generator, not the plugin.
The initial soak preceded the final premultiplied blend correction; the final results
above supersede it for release validation.

violating the live timing target. Camera exposure/lighting and microphone sync remain
manual adjustments, with instructions and restoration guidance in the README.
